MnemoToad Platform Architecture

A living reference for the schema and service boundaries behind the edutainment platform: Knowledge (a ConceptNet-style graph of things), Learning (a Leitner-box spaced-repetition scheduler), and the future App Server that composes them for the frontend.

§0 Key decisions

Four calls this whole design hangs on

Everything below follows from these — worth re-reading before questioning any individual table or endpoint.

1

Attributes are graph-adjacent, not a jsonb bag

Entity-valued attributes (a country's capital) are KnowledgeRelation rows. Scalar literals are rows too — one KnowledgeNodeAttribute row per node+key, composite-keyed, no separate lookup table — since this Postgres schema is a stepping stone to a future graph database. Each row's Value is itself jsonb, so Postgres stays type-aware without a stored datatype column.

2

Media is always a URL

No blob storage in Knowledge, ever — just a URL, catalogued and linked to a node by key, one node per asset. Everything else about that link (accessibility text, arbitrary metadata) lives on the link itself, not the URL.

3

Single user, for now

No ownership model yet. Box/schedule state lives directly on the card. Templating and per-user deck cloning are a deliberately deferred future phase.

4

Cards are N-faced & live

Faces store a path expression, not a value — resolved fresh against Knowledge, with a cached copy to detect drift.

Knowledge§1

Attributes

A normalized attribute table, not a single jsonb blob column. KnowledgeNodeAttribute links a node directly to a scalar value by key — (knowledge_node_id, key) composite primary key, no separate AttributeType lookup table (an earlier version had one; it turned out to just duplicate what the key string already says, once Value itself became genuinely typed). Value is native Postgres jsonb, so Postgres stays type-aware (string vs. number vs. boolean) without a stored datatype column. Entity-valued attributes (a country's capital, its currency) stay KnowledgeRelation rows to other nodes instead. The API embeds attributes directly in the KnowledgeNode JSON (POST/PUT/GET /nodes) rather than through a separate resource — full-replace on update, scalars only for now (no arrays or nested objects).

France: canonicalName: "France", plus attributes: { isoCode: "FR", population: 68000000 }, plus a hasCapital relation to a "Paris" node. Text-only cards work automatically — a node with no attributes or media is still a complete card. Reconsidered twice: first away from an earlier properties jsonb column on the node (filtering/searching by a specific attribute's value wants native SQL, and this schema is a stepping stone toward an eventual graph-database migration anyway, so "jsonb avoids a join" doesn't carry much weight — graph traversal already means joins); then away from a name-lookup AttributeType table once Value itself became jsonb-typed and a stored datatype column had nothing left to do.

Knowledge§2

Media

Every MediaAsset is a URL — a third-party link (flags via flagcdn.com for v1) today, a future self-hosted Azure component's URL later, no distinguishing flag needed until that day comes. Knowledge is a catalog, not a media host: no blob storage, no dimensions, no mime type — and it isn't the source of truth on whether an asset ID is even valid, either. KnowledgeNodeMedia links a node to an asset by a plain string key, composite-keyed the same way KnowledgeNodeAttribute is (no separate role lookup table), but with no foreign key back to media_asset — that existence check is deferred to a future dedicated media server, not owned here. Each MediaAsset backs at most one KnowledgeNodeMedia row, enforced by a plain unique constraint — sharing one asset across nodes isn't supported; two nodes wanting the same picture each get their own MediaAsset row. alt_text is required on every link (accessibility, not optional), and an open metadata column holds the entire submitted stanza verbatim — including id and alt_text again, redundantly — so arbitrary extra fields round-trip without the API needing to know about them.

Knowledge§3

Property path DSL

A small custom grammar for pulling a single value out of the graph, starting from a node — how LeitnerCardFace describes what to quiz on. No existing standard matches this exact compact form; it borrows JSONPath's property-access notation and Cypher/Gremlin's traversal steps.

path := hop* terminal hop := ('>' | '<') name -- follow a KnowledgeRelation by RelationshipType.Name, forward (>) or backward (<) terminal := column | attribute | media column := '_' name -- a KnowledgeNode column: id | canonicalName | description attribute := '.' name -- KnowledgeNodeAttribute.Value where Key = name media := '#' name -- KnowledgeNodeMedia where Key = name, resolves to { id, alt_text, metadata? } (no url)
PathResolves to
_canonicalNameThe node's own name
#flagThe node's own flag media
.populationThe node's KnowledgeNodeAttribute row where Key = "population"
>capital_canonicalNameFollow capital forward to another node, then its name
<capital_canonicalNameFollow capital backward — from the target of a capital relation back to its source — then its name
>partOf>partOf_canonicalNameTwo hops (city → region → country), then name
>partOf<capital_canonicalNameMixed-direction hops are allowed — direction is per-hop, not per-path
literalLearning-only sentinel: skip resolution, use the card face's cached value as-is

Surface syntax is unchanged since the earlier jsonb-column design — .name still means "this node's scalar attribute called name" — only the resolution mechanism has moved twice: from a jsonb key lookup on a single blob column, to a join against attribute_type/knowledge_node_attribute, and now to a direct keyed lookup on (knowledge_node_id, key) — no join at all, now that attribute_type is gone.

Implemented as POST /nodes/resolve, resolved in bulk — one call accepts many (nodeId, paths[]) entries, the whole reason the future App Server's due-cards read path stays at two HTTP calls, however many cards are due. A path that can't be resolved (missing node, hop, or attribute/media key) fails just that one path, not the batch. A sibling endpoint, POST /nodes/resolve/type, takes a NodeType name instead of an explicit node list — it finds every KnowledgeNode of that type and resolves the same paths against each in one call. 404 if the NodeType name itself doesn't exist, 200 with an empty list if it exists but has no nodes yet. This is what deck generation (below) uses to seed a deck's cards without a separate GET /nodes call first.

Every name in a hop or terminal — a RelationshipType.Name, or an attribute/media key — is DB-constrained to letters only (no digits, no punctuation): _/./#/>/< are the grammar's own delimiters, so a name containing one is ambiguous to parse. Discovered, not originally planned — NodeType.Name/KnowledgeNode.CanonicalName stay unrestricted, since neither is ever parsed as DSL syntax.

Both directions match the same RelationshipType.Name column — there's no separate inverse-name column. An earlier InverseName column existed briefly for this and was removed; reverse traversal instead reuses Name, walking a matched relation backward, behind its own explicit < token rather than a silent fallback on >.

— Schema

Entity relationships

Knowledge and Learning are separate Postgres databases on the same server. The dotted line below is the one place that matters: Learning references a Knowledge node by bare UUID, with no real foreign key — Postgres can't enforce a constraint across databases.

Learning§4

Leitner-box domain model

Box 0 is new/just-missed and immediately due. Correct answers promote toward the highest configured box; a miss drops straight back to 0. No ReviewLog — box state is overwritten in place, not appended as history.

The schedule (how far out each box due-dates, plus jitter) is a real table, leitner_schedule, not config — data-driven from the outset even though only one global schedule exists today.

App Server§5

Composition layer

Knowledge owns content, Learning owns scheduling, and App Server is the only layer that knows about both — a BFF with no database of its own, sitting between the frontend and the two service APIs.

— API interactions

Who calls whom

flowchart LR
    FE["React Frontend"] --> AS["App Server"]
    AS --> K[("Knowledge API")]
    AS --> L[("Learning API")]
    L -. "generation only — the one exception" .-> K

Every other arrow is the only path allowed — the frontend never calls Learning or Knowledge directly, and Learning never calls Knowledge outside deck generation.

sequenceDiagram
    participant FE as Frontend
    participant AS as App Server
    participant L as Learning
    participant K as Knowledge

    FE->>AS: GET due cards
    AS->>L: GET /leitnerDecks/{id}/due
    L-->>AS: cards + faces (path, cachedValue)
    AS->>K: POST /nodes/resolve (batched)
    K-->>AS: resolved values
    AS->>AS: diff vs cachedValue
    AS-->>FE: cards + values + drift flags

Due cards — two HTTP calls total, regardless of how many cards are due.

sequenceDiagram
    participant U as Caller
    participant L as Learning
    participant K as Knowledge

    U->>L: POST /leitnerDecks/generate
    L->>K: POST /nodes/resolve/type (nodeTypeName + paths)
    K-->>L: resolved values, per matching node
    L->>L: create deck + cards + faces (seeded from resolved values)
    L-->>U: deck created

Deck generation — the one narrow, explicit Learning→Knowledge exception. One call now, not two — POST /nodes/resolve/type finds every matching node and resolves the seed paths against each in a single round trip.

§6 Frontend

React first, native later

React web talks only to the App Server. React Native is an explicit later phase — if adopted, the App Server's contract is the reusable asset, not necessarily UI code.
